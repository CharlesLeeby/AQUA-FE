## 2026-09-04 — Positive-window coverage expansion direction audit

### Task Objective

Assess whether AQUA-FE can increase the proportion of windows that improve over
KLT without weakening the protected-backbone/no-harm contract.

### Problem / Motivation

The user identified that dataset-level presence of a positive is less important
than the within-dataset positive-window rate. Current outcome-blind frontend
evidence shows very sparse XFeat-v3 intervention, which risks making the system
indistinguishable from KLT on most windows.

### Files Changed

- `papers/frontend_positive_window_rate_expansion_v1/research-question-card.md`
- `docs/RESEARCH_LOG.md`
- `docs/CODEX_WORKLOG.md`

### Implementation

Created an exploratory research question card and appended the corresponding
paper-oriented reasoning record. No source code, gate, configuration, frozen
protocol, dataset, feature bag, or backend artifact was modified.

### Technical Decisions

- Rejected simple gate relaxation because prior replacement experiments show
  that even three early swaps can trigger a wrong-scale branch.
- Did not revive the failed QG marginal-support ranker. The proposed hypothesis
  concerns detecting KLT geometry risk before source routing, not optimizing an
  already-eligible measurement set.
- Prioritized completing the existing frozen backend matrix because SP+LG is
  already active in 8/12 windows while XFeat-v3 is active in only 1/12; this
  cleanly tests source/candidate supply without retuning.
- Preserved protected KLT, exact inactive fallback, small action dose, and a
  mandatory matched classical-source attribution control.

### Experiments Performed

Not evaluated. No new frontend run, VINS replay, ablation, parameter sweep, or
trajectory evaluation was performed.

### Quantitative Results

Existing artifact inspection found 12/12 frontend PASS cells for each arm in
the current confirmatory matrix. XFeat-v3 is active in 1/12 windows with two
exported observations; SP+LG is active in 8/12 windows with 357 exported
observations. These are frontend action counts, not trajectory improvements.

### Qualitative Observations

- The immediate bottleneck may be XFeat-v3 opportunity recall or source supply,
  because another frozen learned source acts on substantially more windows.
- Known positive KLT streams can be feature-count saturated yet geometrically
  weak, so count/overlap collapse is not a sufficient trigger.
- Existing geometry metrics and source-specific hooks make an export-only
  opportunity audit feasible, but effectiveness is Not evaluated.

### Failed Attempts

None. Prior project failures were inspected and retained as design constraints.

### Known Issues

- Backend outcomes for the 12-window confirmatory matrix remain Not evaluated.
- The suggested geometry-risk signals are Hypothesis / Inference, not a
  validated selector.
- An unrelated ROS/VINS experiment from another workspace was active during
  inspection and was not touched.
- Commit and Branch: Unknown (project Git metadata unavailable).

### Interpretation

There is a plausible path to a higher positive-window rate, but it depends on
improving conditional action quality and opportunity coverage rather than
opening the current gate indiscriminately. The current evidence does not yet
show that additional SP+LG or geometry-routed action improves trajectories.

### Next Steps

Finish the existing frozen 12-window backend comparison. Based on its complete
outcomes, decide whether to retain a single XFeat source, add source-specific
routing, or stop learned expansion. Any new method requires a separate
development branch and untouched confirmatory windows.
